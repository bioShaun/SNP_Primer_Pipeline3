## 核心问题

当前测试体系有两层问题。

### 第一层：语义混乱（原始报告已覆盖）

1. `e2e` 这个词被不同类型测试复用。
2. 原 `test_integration.py`（现为 `test_module_basics.py`）实际是 Unit。
3. `consistency` 目录内部各文件层级不同但被统一对待。
4. pytest marker 已声明但没有成为稳定约定。

### 第二层：覆盖缺位（原始报告未覆盖）

1. 核心业务模块覆盖率已显著改善（caps 47%、parser 59%），但仍有提升空间；其余模块（kasp 85%、blast 84%、alignment 86%）已补齐显式 unit 测试。
2. 关键纯函数（`_calculate_subject_snp_position`、`find_variant_sites_v2`、`_reverse_complement` 三份实现）均已补齐显式 unit 测试。
3. 已知的正确性问题（target 序列选择脆弱）**进度**：已有 **`@pytest.mark.xfail`** 用例描述期望行为（见 `tests/test_regression_process_snp_target.py`）。
4. 空文件 `test_kasp_consistency_fixed.py`：**进度**：已从仓库中删除。

## 重构前补测试的特殊约束

在"先补测试、再重构"的场景下，需要特别注意一个问题：

**不要为已知有 bug 的行为编写"保护性测试"。**

评估报告 #1 已经确认：`process_snp()` 中 target 序列的选择依赖"第一条命中"，这是一个正确性风险。如果先写测试锁定当前行为，重构修正 bug 时这些测试会失败，产生"绿变红"的误导。

正确做法：

- 对已知有 bug 的行为：写测试描述**期望的正确行为**（TDD 风格，先红后绿），用 `@pytest.mark.xfail(reason="已知问题 #1：target 序列选择脆弱")` 标记。
- 对行为正确但缺少测试的纯函数：写测试锁定当前正确行为。
- 对行为不确定的逻辑：先审查确认行为是否正确，再决定测试策略。

## 推荐的测试分层

### 1. Unit

定义：

- 针对单个函数、类或局部逻辑。
- 不依赖完整流程，不依赖真实外部工具链（BLAST、Primer3、Muscle）。
- 纯函数测试应 mock 所有外部依赖。

适用内容：

- query id 解析、IUPAC 转换、reverse complement
- `_calculate_subject_snp_position`、`_create_flanking_region` 等纯函数
- BTOP 解析、3' 端匹配检测
- Primer3 输出解析
- 数据模型序列化

### 2. Integration

定义：

- 覆盖多个模块协作，**实际执行了 V3 代码的跨模块逻辑**。
- 可以使用测试数据、受控输入、局部真实依赖。
- 不要求完整从用户输入跑到最终产物。

不属于 Integration 的情况：

- 仅做类实例化或 import 验证 → Smoke。
- 仅校验 V2 参考数据的属性（如 DNA 合法性、Tm 范围）但不执行 V3 逻辑 → Reference-validation。

适用内容：

- parser → FASTA 生成链路
- BLAST 结果解析 → flanking region 提取链路
- alignment → variant site 检测链路
- KASP/CAPS 设计的子链路验证
- consistency 目录中实际执行了 V3 跨模块逻辑的测试（如 `test_parser_consistency.py`、`test_kasp_consistency.py`）

### 3. E2E

定义：

- 从用户可见入口开始。
- 调用真实主流程 `run_pipeline()`。
- 验证关键输出是否生成且满足预期。

适用内容：

- 使用示例输入文件和测试数据库，完整跑一遍流程
- 验证中间文件和最终文件存在、结构正确、关键结果可用

建议归类：

- `tests/test_end_to_end.py`

### 4. Manual / Real-world

定义：

- 依赖真实外部环境、真实数据库、真实工具链或历史参考输出。
- 运行成本高，不适合作为默认 PR 回归集。

建议归类：

- `tests/manual/test_full_pipeline.py`
- `tests/manual/test_e2e_real.py`

## CI / 执行策略建议

### 选用黑名单 marker 过滤，不用白名单

历史草案曾建议 `pytest -m "unit or integration or e2e"`。这属于**白名单**策略，存在一个关键问题：任何未打 marker 的新测试会被**静默排除**，本质上和当前 consistency 目录的静默跳过是同一类陷阱。忘打 marker 不会在 CI 里表现为失败，只会表现为"覆盖少了但没人发现"。

因此统一采用**黑名单 marker**策略：新测试默认会被跑到，只有显式标记为 `manual` / `slow` 的才会被排除。配合 `--strict-markers` 可以同时约束 marker 拼写。

### 本地开发默认

```bash
pytest -m "not manual and not slow" --strict-markers
```

目的：快速反馈，支持 TDD；未标记的测试默认会跑。

### PR / 常规 CI

```bash
pytest -m "not manual" --strict-markers
```

目的：保持主干稳定；包含 e2e 和 slow 但排除高成本 manual。

### 发布前 / 定时任务

```bash
pytest --strict-markers  # 全量运行，包括 manual
```

目的：在更接近真实环境的条件下做高成本验证。
