# SNP_Primer_Pipeline3 测试分层策略建议

## 文档目的

基于当前测试目录结构和代码审阅结果，给出一套测试分层方案。

核心目标：在重构之前把测试补齐，为后续重构提供安全网。

本文档不涉及代码修改，仅用于后续测试补齐、体系整理和 CI 设计参考。

## 当前现状

### 覆盖率概览

以下数据来自 `python -m pytest -q` 全量运行（90 passed, 105s），包含 Unit、Integration、Consistency、E2E 全部测试。

| `models.py` | 85% | 数据模型，覆盖良好 |
| `core/alignment.py` | 85% | 主要由 E2E 和 consistency 测试间接覆盖 |
| `primers/kasp.py` | 79% | 主要由 E2E 测试间接覆盖，缺少显式 unit 测试 |
| `core/blast.py` | 78% | 主要由 E2E 测试间接覆盖，缺少显式 unit 测试 |
| `main.py` | 71% | 主流程编排，由 E2E 测试覆盖 |
| `core/primer3_parser.py` | 69% | Primer3 接口层 |

| `exceptions.py` | 62% | 异常类 |

关键观察：

- 多数模块的覆盖率来自 E2E 和 consistency 测试的**间接执行**，而非**显式 unit 测试**。
- 间接覆盖意味着：这些行被执行过，但没有针对性的断言来锁定其行为。重构时如果改变了中间逻辑但最终输出不变，间接覆盖不会捕获回归。
- `caps.py`（24%）和 `parser.py`（42%）是覆盖率最低的两个核心模块。

内容：验证 import、config 创建、异常类、model 序列化。

#### 2. `tests/test_blast_query_id_parsing.py` — 实际层级：Unit

内容：测试 `FlankingExtractor.extract_flanking_regions` 对含下划线 query ID 的解析。

评估：针对单一纯逻辑的 Unit 测试，无问题。

#### 3. `tests/test_specificity.py` — 实际层级：Unit

内容：测试 BTOP 解析、3' 端匹配检测、Fail/Warning/PASS 逻辑、best primer 选择、FASTA 准备。

评估：质量较高的 Unit 测试，覆盖了 specificity 模块的核心逻辑。

#### 4. `tests/test_integration.py` — 实际层级：Unit（命名误导）

内容：

- `test_polymarker_parser_integration` — 单模块解析，无跨模块协作
- `test_kasp_designer_initialization` — 仅验证构造函数
- `test_caps_designer_with_enzyme_file` — 单模块酶库加载
- `test_snp_model_serialization` — dataclass 序列化
- `test_package_imports` — import 验证

评估：所有测试函数都只涉及单模块、无跨模块协作，实际是 Unit 级别。文件名 `test_integration` 造成语义误导。

建议：重命名为 `test_module_basics.py` 或将内容合并到 `test_basic_structure.py`。

#### 5. `tests/test_end_to_end.py` — 实际层级：E2E

内容：使用 `run_pipeline()` 跑主流程，检查输出文件、BLAST 结果、flanking sequences、SNP 目录。

评估：当前最接近正式 E2E 测试的文件。但每个测试函数都独立调用 `run_pipeline()`，存在重复执行开销。

#### 6. `tests/consistency/` — 实际层级：混杂

各文件实际层级不同，需要区分对待：

| 文件 | 实际层级 | 说明 |
|------|---------|------|
| `test_e2e_consistency.py` | Smoke | 只做 import、config 创建、文件结构验证，多处写了 "Skip actual pipeline execution" |
| `test_parser_consistency.py` | Integration | 构造输入 → 跑 parser → 验证输出，真正的跨步骤验证 |
| `test_kasp_consistency.py` | Integration | 依赖 Primer3 和 V2 参考数据，实际运行 KASP 设计并验证结果 |
| `test_kasp_consistency_fixed.py` | 死文件 | 空文件，应删除 |
| `test_blast_consistency.py` | Smoke / Reference-validation | 明确写了 "Skip actual BLAST execution for now"，只做类实例化和 V2 参考数据属性校验 |
| `test_alignment_consistency.py` | 待确认 | 依赖 V2 参考数据 |
| `test_flanking_consistency.py` | 待确认 | 依赖 V2 参考数据 |
| `test_caps_consistency.py` | Smoke / Reference-validation | 不执行 V3 CAPS 设计，只校验 V2 参考数据属性（DNA 合法性、位置、Tm 范围等） |

共性问题：所有 consistency 测试依赖 `test_data/v2_examples` 目录，当数据不存在时会 `pytest.skip` 静默跳过，导致 CI 中可能 0 个测试实际执行却显示"全部通过"。

#### 7. `tests/manual/` — 实际层级：Manual

- `test_full_pipeline.py` — 从头跑完整 V3 pipeline
- `test_e2e_real.py` — 借助 V2 中间产物比较

评估：高成本、强环境依赖，不适合默认自动执行。

## 核心问题

当前测试体系有两层问题。

### 第一层：语义混乱（原始报告已覆盖）

1. `e2e` 这个词被不同类型测试复用。
2. `test_integration.py` 实际是 Unit。
3. `consistency` 目录内部各文件层级不同但被统一对待。
4. pytest marker 已声明但没有成为稳定约定。

### 第二层：覆盖缺位（原始报告未覆盖）

1. 核心业务模块（caps 24%、parser 42%）覆盖率偏低；其余模块（kasp 79%、blast 78%、alignment 85%）虽然覆盖率较高，但主要来自 E2E 间接执行，缺少显式 unit 测试来精确锁定行为。
2. 关键纯函数（`_calculate_subject_snp_position`、`find_variant_sites_v2`、`_reverse_complement` 三份实现）已被 E2E 间接执行，但没有针对性的显式 unit 测试。
3. 已知的正确性问题（target 序列选择脆弱）没有对应的测试来定义期望行为。
4. 存在空文件（`test_kasp_consistency_fixed.py`）和死代码。

## 重构前补测试的特殊约束

在"先补测试、再重构"的场景下，需要特别注意一个问题：

**不要为已知有 bug 的行为编写"保护性测试"。**

评估报告 #1 已经确认：`process_snp()` 中 target 序列的选择依赖"第一条命中"，这是一个正确性风险。如果先写测试锁定当前行为，重构修正 bug 时这些测试会失败，产生"绿变红"的误导。

正确做法：

- 对已知有 bug 的行为：写测试描述**期望的正确行为**（TDD 风格，先红后绿），用 `@pytest.mark.xfail(reason="已知问题 #1：target 序列选择脆弱")` 标记。
- 对行为正确但缺少测试的纯函数：写测试锁定当前正确行为。
- 对行为不确定的逻辑：先审查确认行为是否正确，再决定测试策略。

## 推荐的测试分层

### 1. Unit

定义：

- 针对单个函数、类或局部逻辑。
- 不依赖完整流程，不依赖真实外部工具链（BLAST、Primer3、Muscle）。
- 纯函数测试应 mock 所有外部依赖。

适用内容：

- query id 解析、IUPAC 转换、reverse complement
- `_calculate_subject_snp_position`、`_create_flanking_region` 等纯函数
- BTOP 解析、3' 端匹配检测
- Primer3 输出解析
- 数据模型序列化

### 2. Integration

定义：

- 覆盖多个模块协作，**实际执行了 V3 代码的跨模块逻辑**。
- 可以使用测试数据、受控输入、局部真实依赖。
- 不要求完整从用户输入跑到最终产物。

不属于 Integration 的情况：

- 仅做类实例化或 import 验证 → Smoke。
- 仅校验 V2 参考数据的属性（如 DNA 合法性、Tm 范围）但不执行 V3 逻辑 → Reference-validation。

适用内容：

- parser → FASTA 生成链路
- BLAST 结果解析 → flanking region 提取链路
- alignment → variant site 检测链路
- KASP/CAPS 设计的子链路验证
- consistency 目录中实际执行了 V3 跨模块逻辑的测试（如 `test_parser_consistency.py`、`test_kasp_consistency.py`）

### 3. E2E

定义：

- 从用户可见入口开始。
- 调用真实主流程 `run_pipeline()`。
- 验证关键输出是否生成且满足预期。

适用内容：

- 使用示例输入文件和测试数据库，完整跑一遍流程
- 验证中间文件和最终文件存在、结构正确、关键结果可用

建议归类：

- `tests/test_end_to_end.py`

### 4. Manual / Real-world

定义：

- 依赖真实外部环境、真实数据库、真实工具链或历史参考输出。
- 运行成本高，不适合作为默认 PR 回归集。

建议归类：

- `tests/manual/test_full_pipeline.py`
- `tests/manual/test_e2e_real.py`

### consistency 目录静默跳过风险处置

所有 consistency 测试依赖 `test_data/v2_examples`，数据不存在时 `pytest.skip` 会导致 CI 中 0 个测试实际执行却显示通过。

注意：`--strict-markers` 只能防止未声明的 marker，不能检测 session fixture 中 `pytest.skip()` 导致的整批跳过。

有效的缓解方式：

- 在 CI 中检查 collected / skipped 计数，当 consistency 测试全部被跳过时报警或失败。
- 或在 `conftest.py` 中将 `v2_examples` 不存在从 `skip` 改为显式失败，确保 CI 能发现数据缺失。

## Marker 策略建议

### 推荐 marker

- `@pytest.mark.unit`
- `@pytest.mark.integration`
- `@pytest.mark.e2e`
- `@pytest.mark.slow`
- `@pytest.mark.manual`

### 推荐约定

- `unit`：默认开发时高频运行
- `integration`：PR 默认运行
- `e2e`：在具备外部工具环境时运行
- `manual`：不进入默认 CI，仅手工触发

### 最小落地建议

1. 给 `tests/test_end_to_end.py` 增加 `@pytest.mark.e2e`。
2. 给 `tests/manual/*` 增加 `@pytest.mark.manual`。
3. 给 `tests/consistency/*` 按内容分别标记为 `integration`（如 `test_parser_consistency.py`、`test_kasp_consistency.py`）或 `smoke`（如 `test_e2e_consistency.py`、`test_blast_consistency.py`、`test_caps_consistency.py`）。
4. 给新增的 Unit 测试统一标记 `@pytest.mark.unit`。

## CI / 执行策略建议

### 本地开发默认

```bash
pytest -m "unit or integration" --ignore=tests/manual
```

目的：快速反馈，支持 TDD。

### PR / 常规 CI

```bash
pytest -m "unit or integration or e2e" --ignore=tests/manual
```

目的：保持主干稳定。

### 发布前 / 定时任务

```bash
pytest  # 全量运行
```

目的：在更接近真实环境的条件下做高成本验证。

## 建议的落地顺序

1. **删除空文件** `test_kasp_consistency_fixed.py`。
2. **重命名** `test_integration.py` → `test_module_basics.py`，`test_e2e_consistency.py` → `test_pipeline_smoke.py`。
3. **补 P0 Unit 测试**（`_calculate_subject_snp_position`、`_reverse_complement` 等纯函数）。
4. **写 xfail 测试**（target 序列选择等已知问题）。
5. **补 P1 Unit 测试**（`_generate_primer3_inputs_v2`、`_convert_to_v2_format` 等）。
6. **给所有测试文件补 marker**。
7. **接入 CI 分层执行策略**。

步骤 1-4 构成重构的最小安全网，步骤 5-7 可在重构过程中逐步完成。

## 最终建议

当前项目的测试问题不只是"语义混乱"，更关键的是"核心业务逻辑的 Unit 覆盖严重不足"。

重构前最值得做的事情，按优先级排序：

1. 给核心纯函数补 Unit 测试（P0 清单），这是重构安全网的基础。
2. 用 xfail 测试标记已知 bug 的期望行为，为重构提供明确的"绿灯"目标。
3. 整理现有文件命名和分层，消除语义混乱。
4. 把 marker 和 CI 策略落地。

一句话总结：先补 Unit，再理分层，不要为已知 bug 写保护性测试。
